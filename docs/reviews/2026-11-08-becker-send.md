# Becker send regression — historical comparison and host reproduction

2026-11-08. Authorized bounded WP4/WP5 investigation of R01/R03/R04. Source comparison and a host test establish the minimum send correction. Application deployment and physical acceptance remain open.

## Sources and historical baseline

- **Reported:** [XCSoar PR #189](https://github.com/XCSoar/XCSoar/pull/189) describes successful tests by eku60 with an AR6201 on Linux and Windows serial ports, including active/standby changes, power cycling and disconnects. The report does not identify a binary hash or all test frequencies.
- **Rechecked source:** the driver's [cd818c90ebb6e803a4b7a804935d87a7575eaa6f revision](https://github.com/eku60/XCSoar/blob/cd818c90ebb6e803a4b7a804935d87a7575eaa6f/src/Device/Driver/AR62xx.cpp), dated 2019-05-03, belongs to that PR. PR head 6d615c04fedb6d243cb664f40daa0b945f4cfdb2 retains its counted send call. This is the source associated with the reported tests, with exact tested-binary identity unresolved.
- **Rechecked source:** [OpenSoar 7.46.26 driver](https://github.com/OpenSoaring/OpenSoar/blob/b2e745cfddfe0150f6ed7db467ac18c321b38d01/src/Device/Driver/AR62xx.cpp), [Port.hpp](https://github.com/OpenSoaring/OpenSoar/blob/b2e745cfddfe0150f6ed7db467ac18c321b38d01/src/Device/Port/Port.hpp) and [Port.cpp](https://github.com/OpenSoaring/OpenSoar/blob/b2e745cfddfe0150f6ed7db467ac18c321b38d01/src/Device/Port/Port.cpp), all at b2e745cfddfe0150f6ed7db467ac18c321b38d01.
- **Rechecked source:** [2024-03-05 commit 7a575346](https://github.com/eku60/XCSoar/commit/7a575346b71c2384420d275b335f36d3078d327d), titled “resolve error in Send-command”, replaces an invalid pointer-to-span reference cast with the char-pointer call and marks msg_size maybe_unused. Its parent already had a broken span adaptation. This identifies the introduction of the current string-length behavior in this lineage, without claiming every intervening version worked.

## Measured host reproduction

[check_becker_send.py](../../tools/check_becker_send.py) downloads pinned sources and compiles the actual 7.46.26 Send, SetAR620xStation, Freq2Idx, Frq2Idx and CRCBitwise function bodies. It also uses the original Port string_view forwarding body and matching overload signatures. The final byte-span port sink captures bytes in memory. Mutexes are host mutexes, the condition wait is a no-op stub, and the initial active/standby state is explicitly synthetic and known. The test neither supplies a radio reply nor models a radio protocol implementation.

The corrected copy of Send differs only at its FullWrite call. The independent expectation is preservation of the entire generated byte buffer, irrespective of radio protocol validity. The old counted call is verified in source, while the historical full application is not compiled.

| Synthetic active / requested standby (MHz) | Original 7.46.26 bytes reaching sink | Corrected Send | Original return |
| --- | --- | --- | --- |
| 118.000 / 123.500 | 4 / 10 | 10 / 10, exact byte match | true |
| 123.000 / 118.000 | 6 / 10 | 10 / 10, exact byte match | true |
| 123.000 / 124.000 | 10 / 10 | 10 / 10, exact byte match | true |
| 121.500 / 123.450 | 10 / 10 | 10 / 10, exact byte match | true |

First generated frame is `A5 14 05 16 00 00 03 70 53 17`. The original call passes only `A5 14 05 16` to the binary sink. Truncation occurs before TCP or serial transport. **Inference:** a transparent ESP32 bridge cannot recover the omitted suffix. Zero-free cases explain how partial functional success can coexist with this defect, without reconstructing the historical tests.

## Minimum changes and open decisions

1. **Required for binary transmission, reproduced:** pass an explicit byte span in Send. The tested replacement is `port.FullWrite(std::as_bytes(std::span{msg, msg_size}), env, CMD_TIMEOUT);`. Retain a regression covering embedded zeros and zero-free commands. This is a local one-call fix, with no demonstrated need for a new UI or driver.
2. **Required for R01 before operational standby use:** represent active frequency as unknown until valid reception and invalidate stale state on reconnect. The combined command must not consume uninitialized/stale state. A refresh/query or a dedicated standby command must be selected from matched protocol evidence. Changing the constructor to an arbitrary default frequency would not meet R01.
3. **Required for R04:** distinguish successful transport from confirmed standby state. Use documented response/readback behavior. ACK/NAK constants in the source are insufficient evidence for standalone acknowledgment bytes. The precise app UI/status changes depend on tracing the caller and the actual protocol.
4. **Receive-side correctness:** bound frame/command lengths before field access, own parser state per instance, and parse payload A5 according to frame length. Recheck CRC exceptions and reception during Send against protocol evidence. These are targeted follow-up increments, whose physical necessity and acceptance need independent vectors and device tests.

For the isolated bridge increment, exact binary transport can be tested independently. The send fix removes the measured transport failure, while complete standby acceptance still depends on the remaining state/receive checks. No estimate of a broad application rewrite follows from this investigation.

## Verification summary

**Measured:** Ubuntu via WSL, g++ 13.3.0 (Ubuntu 13.3.0-6ubuntu2~24.04.1), C++20 with AddressSanitizer and UndefinedBehaviorSanitizer. Run `python3 tools/check_becker_send.py --compiler g++` in Linux/WSL with network access. All four original-outcome assertions and all four corrected byte-equality assertions passed, with no sanitizer findings in the exercised paths. Reviewed GPL headers before temporary extraction, upstream bodies remain downloaded temporary inputs. The repository contains the independently written test scaffold and documentation. Checked documentation links and diff whitespace. No full Android/OpenSoar build, live TCP capture, ESP32 execution, physical radio response or aircraft test was performed. Historical reports remain reported evidence.
