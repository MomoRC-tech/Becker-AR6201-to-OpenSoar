# Bridge firmware 0.5.4: review of five static findings

S138, 2026-11-19 · WP6 · firmware 0.5.4 at `4a2bda5`, Arduino-ESP32 3.3.12 (ESP-IDF 5.5.5) · bench coverage S111, S116, S119, S120

A static review raised five findings against firmware 0.5.4. Each was checked as a hypothesis against the sketch and the installed core sources: does it hold, how likely is the trigger, and what does it do to OpenSoar's data?

> [!NOTE]
> Source reading only, plus the existing bench records. No test was run on the bridge for this review. Finding 5 was fixed in firmware 0.5.5 (S139); the other checks and the finding 3 fix are [open items](../../project/open-items.md#software-and-acceptance).

## 1. TCP-to-UART write

- **Trigger:** apps send more to one instrument than its baud rate carries, for longer than a burst: one app above 19200 baud, or several apps whose sum is.
- **Why it blocks:** the core installs the UART driver with no transmit buffer (`_txBufferSize(0)`, `HardwareSerial.cpp:142`). With none, `uart_write_bytes()` returns only once all data is in the 128-byte FIFO (`uart.h:518-519`, `soc_caps.h:358`).
- **How long:** the wire time of everything but the last 128 bytes. Each pass reads up to 1023 bytes per app (`bridge.ino:580-588`): at most about 0.47 s per app at 19200 baud. The radio reads up to 1024 bytes (`:277-279`): about 0.93 s at 9600 baud. No flow control is set up, so the write always ends.
- **Impact:** one burst only delays the other ports; their 4096-byte receive buffers hold about 2.1 s at 19200 baud. Under sustained overload with two or more writers a pass takes over 0.53 s, while the loop reads at most 1024 bytes per port per pass, so a busy FLARM or Zander receive buffer would overflow.
- **Short writes are not reported:** `HardwareSerial::write()` returns `size` unconditionally (`HardwareSerial.cpp:586-589`); `uartWriteBuf()` ignores the driver's return value (`esp32-hal-uart.c:1771-1778`). The radio short-write branch at `bridge.ino:282-285` cannot run.
- **Bench coverage:** S119 and S120 sent 80 % of the wire rate with one writer: worst delay 0.25 s, no receive errors. Not covered: two writers above the wire rate together.

## 2. Client slots after a clean close

- **Hypothesis:** core 3.3.12 `connected()` treats a zero-length `recv()` as connected (`NetworkClient.cpp:571-600`), so a closed app keeps its slot until instrument data makes the send fail.
- **Against it:** `tools/log_test.py` closes a Zander app while nothing arrives on that UART and expects "Zander: 0 apps connected" within 2.5 s. It passed in S116 and S120; `bridge.ino` is unchanged since 0.5. That count uses the same `operator bool` → `connected()` test as the slot check at `bridge.ino:547` (`NetworkClient.h:76`).
- **Likely mechanism (lwIP source as known, not checked on disk):** the first `recv()` after the FIN returns 0, the next one −1 with ENOTCONN, which `connected()` treats as disconnected.
- **Side notes:**
  - A dead slot keeps its socket in CLOSE_WAIT until the next app connects to that port. The upstream `continue` at `:557` then frees it (socket closed through the shared handle, `NetworkClient.cpp:170`).
  - The same `continue` lets `:561` drop a second connection that arrives in the same pass, even with free slots.
- **Not covered:** repeated closes on a quiet port; S116 closed one app.

## 3. Settings rollback and failed save

- **(a) Rollback:** `copyNamespace()` clears the target first (`settings.h:409-413`), and every Preferences call commits on its own (`Preferences.cpp:66-80`). The rollback after the 10 min timeout (`:476-478`) or at the 4th start (`:449-451`) erases the trial marks `tr` and `tc` before it copies up to 22 keys.
  - **Trigger:** a trial that was not kept, plus a power cut during the copy. The copy time was not measured. The start-up rollback runs while the power is being switched on and off, which is what counts the trial starts.
  - **Impact:** some previous values, defaults for the rest. A missing `v` key is accepted (`:538`). There is no retry. The next save that starts a trial copies this mix into the backup as the last good set (`:506`). Changed TCP ports may fall back to their defaults, so OpenSoar cannot connect until the settings are entered again. The hotspot fallback keeps the bridge reachable.
- **(b) Failed save:** `settingsSave()` returns false when the namespace does not open (`settings.h:503`) and ignores write failures (`:395-405`). The handler answers `{"ok":true,"trial":false}` either way and restarts (`settings_page.h:130-132`). After the restart the status page shows the old values.
- **Bench coverage:** S111 states "Not tested: power loss during a save".

## 4. Socket limit

- **Limit:** `CONFIG_LWIP_MAX_SOCKETS 16` and `CONFIG_LWIP_MAX_ACTIVE_TCP 16` in both prebuilt `sdkconfig.h` files of core 3.3.12.
- **Always in use (6):** three bridge listeners, the supply port (`supply.h:61`, sensor on), the web server (`status_page.h:38`) and OTA's UDP socket (`ArduinoOTA.h:118`, `.cpp:173`).
- **Clients (up to 14):** 4 + 4 navigation slots and 1 radio owner (`config.h:63`), 4 supply slots (`supply.h:68`), 1 web client. During an OTA upload the bridge also opens a TCP connection to the PC (`ArduinoOTA.cpp:368`).
- **When all 16 are in use:** `hasClient()` gets no socket from `lwip_accept()` (`NetworkServer.cpp:141-160`), so every new connection fails: navigation, radio, supply, web page and OTA. Existing connections keep running. The app probably sees the connection accepted and then closed (lwIP source as known, not checked on disk).
- **Trigger:** 10 or more client sockets at once. One phone uses 4 and the page 1; two phones 9. It takes about three app instances.

---

## 5. Warning timers

- `supply.h:197-198` and `chiptemp.h:75-76` stored `now | 1u` and compared at once. With `millis()` even, `now - (now + 1)` wraps to 0xFFFFFFFF, so about half of all episodes logged "low for 10 s" or "high for 60 s" on the first reading, into the saved log as well. Forwarding was not affected.
- The `badSince` timer at `supply.h:182` already used `else` and was correct.
- **Fixed in 0.5.5** with the same `else`: the count starts at the first reading and is compared from the next one.
